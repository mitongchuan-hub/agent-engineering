## 解决方案

做一个 **简历 × 岗位 JD 匹配系统**：输入一份简历 + 一批 JD，算出每份的匹配度。

但关键不是功能，是**架构**——"可计算的归规则，可推理的归 LLM"：

```
┌────────────────────────────────────────────┐
│ 规则层（compute_match，确定性）              │
│   技能重合度 / 年限达标 / 学历达标             │
│   → 可审计、可复现、零 token 成本             │
├────────────────────────────────────────────┤
│ LLM 层（推理）                              │
│   写报告、给建议、讲故事                     │
│   → 需要判断力的部分                        │
└────────────────────────────────────────────┘
```
为什么这样分？看这个例子：技能覆盖率 86%、缺口是 Elasticsearch——这些是**事实**，
该由代码算出来；而"建议候选人补 ES 还是转后端岗"是**判断**，该由模型给。

## 工作原理

### ① 打分器三件事

```python
def compute_match(resume_text, jd_text):
    resume_skills = _extract_skills(resume_text)   # 词表命中
    years_ok  = resume_years >= jd_min_years       # "N 年"正则
    edu_ok    = resume_edu   >= jd_min_edu         # 学历等级比较
    overall = skill_coverage*50 + years*25 + edu*25  # 加权总分
```

### ② 为什么"确定性"是卖点

```python
# 同一输入永远同一输出
r1 = compute_match(resume, jd)
r2 = compute_match(resume, jd)
assert r1 == r2   # ✅ 可复现 = 可测试 = 可审计
```
LLM 输出有随机性，规则没有。**把能确定的部分从 LLM 手里拿回来**，
既省钱又给报告提供"锚点"（模型不能瞎编分数）。

### ③ 结果可解释

返回结构化 JSON：`matched_skills / gap_skills / dim_scores / overall_score / verdict`。
自测追问"你的分数怎么来的？"——每个字段都有出处。

## 自测问答

**Q：为什么用规则不用 LLM 打分？**
A：打分是确定计算——LLM 做又贵又飘（同输入可能不同输出）。规则可审计、可复现、零成本；幻觉风险为零。**LLM 只做它擅长的：推理与表达。**

**Q：规则会不会漏？**
A：会。词表匹配识别不了"语义相近"（如 'TypeScript' vs 'TS'）。所以这是**混合架构**：规则给确定性锚点，剩下的语义模糊地带交给 LLM 在报告里补全。

**Q：这个应用你怎么评测它？**
